    ชื่อโครงการ: โครงการพัฒนาระบบข้อมูลและประสานงานเพื่อช่วยเหลือผู้ได้รับผลกระทบจากภัยพิบัติ LCCS
    วันที่จัดทำ: 4 ตุลาคม 2569 (2026-10-04)
    รูปแบบ: TOR ภาพรวมทั้งโครงการ แบ่ง Phase และแยกแพ็กเกจงานที่สามารถพิจารณาจ้างเป็นระยะ
    ฐานหลักฐาน: คลัง LCCS (คลังภายใน) และรายการต้นฉบับ S001–S077

    1. หลักการและเหตุผล

    เอกสาร LCCS อธิบายปัญหาข้อมูลการช่วยเหลือที่กระจายอยู่ในโทรศัพท์ กลุ่มสนทนา ตารางข้อมูล วิทยุ และความจำของผู้ปฏิบัติงาน ทำให้เชื่อมข้อมูลผู้รอความช่วยเหลือ ผู้ให้ความช่วยเหลือ ทรัพยากร และผลการดำเนินงานได้ยาก โดยเฉพาะเมื่อการสื่อสารขัดข้อง [S069, S070, S072, S077]

    โครงการจึงมุ่งสร้างข้อมูลปฏิบัติการที่มีที่มาและตรวจสอบย้อนหลังได้ ตั้งแต่รับข้อมูล ตรวจสอบ สรุปสถานการณ์ ตัดสินใจ มอบหมายงาน ดำเนินการ และส่งผลกลับ เพื่อให้หน้างาน ส่วนวางแผน ส่วนปฏิบัติการ และส่วนสนับสนุนทำงานต่อกันได้

    เอกสารเดิมมีทั้งเส้นทาง ศูนย์พักพิงเป็นจุดเริ่ม และเส้นทาง รับผู้ช่วยและทรัพยากรเป็นจุดเริ่ม ร่างนี้ใช้ศูนย์พักพิงเป็นข้อเสนอสำหรับพิสูจน์แกนข้อมูลและออฟไลน์ก่อน พร้อมเก็บเส้นทางทรัพยากรไว้ในภาพรวม การเลือกเส้นทางจริงต้องปิด Q01 ใน Phase 0 มิใช่ตัดสินจากวันที่แก้ไขไฟล์ [S069, S070, S073, Q01]

    2. วัตถุประสงค์และผลลัพธ์

    1. ให้ผู้ปฏิบัติงานบันทึกข้อมูลขั้นต่ำ ณ จุดช่วยเหลือได้เมื่อไม่มีอินเทอร์เน็ต และรักษาข้อมูลจนส่งส่วนกลางสำเร็จ
    2. ให้ส่วนกลางเห็นจำนวนคน ความจุ ทรัพยากรที่เหลือ และคำขอ พร้อมเวลา แหล่งที่มา และข้อจำกัดของข้อมูล
    3. ให้การรับผู้ช่วย ทีม อุปกรณ์ และสิ่งสนับสนุนเชื่อมกับการตรวจสอบความพร้อม การวางแผน และภารกิจได้เป็นระยะ
    4. ให้ครอบครัวตรวจสอบสถานะที่ได้รับการยืนยันตามสิทธิ์ โดยกำหนดขอบเขตข้อมูลที่เปิดเผยก่อนใช้งาน
    5. ให้การตัดสินใจ การส่งต่อ การใช้ทรัพยากร และการส่งมอบมีผู้รับผิดชอบและประวัติที่ย้อนตรวจได้
    6. ให้ระบบมีเจ้าของ ผู้ดูแล ขั้นตอนทดลองใช้ และเกณฑ์ขยายผลที่ชัดเจน

    ผลลัพธ์ที่ตรวจรับได้: ข้อมูลยังอยู่หลังปิดเปิดแอป; ส่งข้อมูลซ้ำแล้วไม่สร้างธุรกรรมซ้ำ; ยอดคนอธิบายที่มาได้; คำขอมีสถานะและเจ้าของ; ผลค้นญาติไม่แสดงสถานะเกินหลักฐาน; และทีมรับช่วงงานได้จากสิ่งส่งมอบจริง

    เป้าหมายการลดเวลา เพิ่มความครอบคลุม หรือเพิ่มประสิทธิภาพเป็นเรื่องที่ต้องวัดใน Pilot เอกสารนี้ไม่มีฐานเพียงพอที่จะรับรองร้อยละผลสำเร็จ จำนวนผู้ได้รับประโยชน์ หรือความพร้อมใช้งานระดับประเทศ

    4. กระบวนการทำงานและผู้เกี่ยวข้อง

    4.1 กระบวนการของคนก่อนระบบ

    1. รวบรวม: ผู้รับแจ้งและหน้างานบันทึกว่าเกิดอะไร ที่ไหน เมื่อใด จำนวนหรือความต้องการเป็นข้อมูลประมาณหรือยืนยันแล้ว และใครเป็นแหล่งข้อมูล
    2. ตรวจสอบและประเมิน: ผู้รับผิดชอบตรวจความซ้ำ ความครบ ความใหม่ และข้อขัดแย้ง แยกข้อมูลที่ใช้ตัดสินใจได้จากข้อมูลที่ต้องติดตาม
    3. สรุปและแลกเปลี่ยน: ส่วนวางแผนรวมสถานการณ์ สถานะปฏิบัติการ ทรัพยากร ความเสี่ยง และข้อจำกัด เพื่อใช้ในรอบวางแผน
    4. ตัดสินใจ: ผู้มีอำนาจกำหนดเป้าหมาย ลำดับความสำคัญ ผู้รับผิดชอบ และกรอบเวลาปฏิบัติงาน
    5. ดำเนินการและส่งผล: ทีมรับงาน รายงานข้อขัดข้อง ผลการช่วยเหลือ และทรัพยากรที่ใช้
    6. ปรับข้อมูลและส่งต่อเวร: ผู้รับผิดชอบปรับสถานการณ์ พร้อมบันทึกเรื่องค้างและข้อมูลที่ยังขาด

    ลำดับนี้ใช้จัดการข้อมูลตามแนวทางใน S050/S072/S073 ต้องให้หน่วยงานปฏิบัติการทบทวนบทบาทและแบบฟอร์มของตนก่อนใช้จริง ร่างนี้ไม่ได้รับรองการปฏิบัติตามมาตรฐาน ICS ทุกระดับหรือกำหนดให้ซอฟต์แวร์เป็นผู้บัญชาการเหตุการณ์

    4.2 ผู้เกี่ยวข้องและขอบเขตสิทธิ์ที่เสนอ

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    Actor หน้าที่ของคน งานในระบบ ขอบเขตสิทธิ์หลัก
    ผู้ได้รับผลกระทบ/ผู้ดูแล ให้ข้อมูลและแจ้งความต้องการ ให้ข้อมูลขั้นต่ำหรือเติมข้อมูลภายหลัง ข้อมูลของตนหรือรายการที่ได้รับมอบสิทธิ์
    เจ้าหน้าที่จุดพักพิง ลงทะเบียน ตรวจจำนวน อัปเดตของและคำขอ Field App เหตุการณ์/จุด/เวรที่ได้รับมอบหมาย
    ผู้จัดการศูนย์พักพิง รับรองการแก้ยอด ความจุ และการย้าย ทบทวนทะเบียนและข้อขัดแย้ง ศูนย์ที่รับผิดชอบ
    เจ้าหน้าที่รับแจ้ง/ท้องถิ่น รับสัญญาณและติดตามที่มา Signal Intake พื้นที่รับผิดชอบ; ไม่ยืนยันยอดจริงจากรายงานดิบอัตโนมัติ
    ส่วนวางแผน ประเมินข้อมูล จัดภาพรวมและเรื่องที่ต้องตัดสินใจ Situation/Planning Console ดูข้อมูลตามบทบาทและจัดทำ snapshot
    ผู้บัญชาการ/ผู้มีอำนาจ รับรองเป้าหมายและอนุมัติคำสั่ง Decision/Assignment อำนาจตามองค์กร เหตุการณ์ และพื้นที่ที่กำหนด
    ฝ่ายปฏิบัติการ/หัวหน้าทีม รับภารกิจ ดำเนินงาน ส่งรายงาน Mission/Field App ภารกิจและทีมของตน
    ผู้ประสานทรัพยากร/โลจิสติกส์ ตรวจความพร้อม จัดสรร รับส่งของ Resource/Support Console ทรัพยากร คลัง และคำขอที่รับผิดชอบ
    ทีมแพทย์/หน่วยรับส่งต่อ ประเมินและรับส่งต่อโดยผู้มีหน้าที่ Medical Console ข้อมูลการส่งต่อที่จำเป็นตามนโยบาย
    ญาติ/ครอบครัว ขอทราบสถานะ Family Portal เฉพาะผลตอบและข้อมูลที่อนุญาต
    ผู้ดูแลองค์กร/ระบบ จัดผู้ใช้ อุปกรณ์ และการตั้งค่า Admin Console แยกงานดูแลระบบจากสิทธิ์อ่านข้อมูลรายบุคคล
    เจ้าของงบ/ผู้ตรวจสอบ รับรองค่าใช้จ่ายและตรวจหลักฐาน Evidence/Export ขอบเขตงบและการตรวจสอบที่ได้รับมอบหมาย

    รายชื่อหน่วยงานจริง ผู้มีอำนาจอนุมัติ และผู้รับผิดชอบข้อมูลยังต้องแต่งตั้ง การมีชื่อหน่วยงานใน stakeholder map ไม่ใช่หลักฐานว่าหน่วยงานนั้นตกลงเข้าร่วมแล้ว

    5. ขอบเขตระบบและรายการโปรแกรม

    5.1 ขอบเขตโดยรวม

    ประกอบด้วยแกนศูนย์พักพิงและข้อมูลออฟไลน์ ส่วนรับสัญญาณและทรัพยากร ส่วนวางแผนและปฏิบัติการ ส่วนสนับสนุนและส่งต่อ และบริการข้อมูลร่วม โดยขยายผ่านการทดลองที่มีเจ้าของและเกณฑ์ตรวจรับ

    MVP ที่เสนอ: หนึ่งเหตุการณ์ หนึ่งจุดพักพิงที่เตรียมไว้ การลงทะเบียนออฟไลน์ จำนวนคนและความจุ ของเหลือและคำขอ การส่งส่วนกลาง และสถานะสำหรับญาติตามกฎที่รับรอง โดยแยกการพิสูจน์ local persistence ใน Phase 1 จาก Pilot ที่เชื่อมทั้งวงจรใน Phase 2

    5.2 โปรแกรมหรือพื้นที่ใช้งานที่เสนอ

    7 รายการต่อไปนี้เป็น พื้นที่ใช้งานตามบทบาท อาจพัฒนาเป็นแอปเดียวที่แยกสิทธิ์ หรือหลายแอปตามผลออกแบบสถาปัตยกรรม ไม่ได้บังคับให้สร้าง 7 repository หรือ 7 โปรแกรมติดตั้ง

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    รหัส โปรแกรม/พื้นที่ใช้งาน ผู้ใช้หลัก หน้าหรือฟังก์ชันสำคัญ เริ่มใน Phase
    PRG01 ระบบบริหารจัดการกลาง (Admin Console) ผู้ดูแลระบบ/องค์กร ผู้ใช้ สิทธิ์ เหตุการณ์ จุด อุปกรณ์ ปัญหา sync ประวัติและการตั้งค่า 1
    PRG02 แอปภาคสนามแบบออฟไลน์ (Field App) เจ้าหน้าที่จุด/ทีมภาคสนาม เลือกจุด ลงทะเบียน แก้ข้อมูล ดูยอด ของเหลือ คำขอ sync; เพิ่ม mission/report ภายหลัง เริ่ม 1; mission 3B; referral 4 เมื่อเลือก
    PRG03 ระบบภาพรวมและวางแผนส่วนกลาง ส่วนวางแผน/ปฏิบัติการ/ผู้มีอำนาจ สถานการณ์ แหล่งข้อมูล คำขอ ทรัพยากร เป้าหมาย การตัดสินใจ ภารกิจ แผนที่ รายงาน 2–3
    PRG04 ระบบสถานะสำหรับครอบครัวและข้อมูลสาธารณะ ญาติ/ประชาชน ผลตอบสถานะตามสิทธิ์; ข่าวสารที่รับรอง; ช่องทางส่งเรื่องตามขอบเขตที่เลือก เริ่ม 2 ตาม policy; public info 3B; evidence tracking 4 เมื่อเลือก
    PRG05 ระบบรับผู้ช่วยและทรัพยากร บุคคล/ทีม/องค์กร/ผู้สนับสนุน ลงทะเบียนผู้ช่วย ทีม อุปกรณ์ สิ่งสนับสนุน import ติดตามผล review 3
    PRG06 ระบบโลจิสติกส์และหลักฐานการสนับสนุน คลัง/ผู้ประสาน/เจ้าของงบ รับของ lot จัดสรร ขนส่ง รับมอบ vendor คำขอจัดซื้อ แฟ้มหลักฐาน 4
    PRG07 ระบบประสานการแพทย์และส่งต่อ ผู้ประสานการแพทย์/หน่วยรับส่งต่อ คำขอส่งต่อ ปลายทางรับเคส สถานะและหลักฐานการส่งต่อ 4 แบบมีเงื่อนไข

    5.3 บริการเบื้องหลังที่ต้องออกแบบร่วม

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    บริการ หน้าที่ ต้องเริ่มเมื่อ
    Identity/Authorization บัญชี องค์กร บทบาท การมอบสิทธิ์ และ session เริ่มมีผู้ใช้และข้อมูล

    API/Database รักษาข้อมูลหลัก กฎสิทธิ์ version และ transaction เชื่อมข้อมูลส่วนกลาง Phase 2
    Evidence/Files/Audit ประวัติ ที่มา เอกสารแนบและสิทธิ์ไฟล์ ประวัติตั้งแต่บันทึกแรก; ไฟล์เมื่อรวมรูป/เอกสารในขอบเขต
    Notification/Integration แจ้งเตือน เชื่อมช่องทางและบันทึกผลส่ง เริ่มในแอป Phase 2; gateway ภายนอกตามข้อตกลง
    Operations/Monitoring เฝ้าระบบ backup restore deploy และ incident handling ก่อนเปิด Pilot ที่ใช้ข้อมูลจริง

    6. แผนระยะงานและเงื่อนไขผ่านแต่ละ Phase

    6.1 หลักการแบ่งระยะ

    • Phase คือระยะพัฒนาและพิสูจน์ระบบ ไม่ใช่ลำดับเวลาของเหตุภัยพิบัติจริง สัญญาณก่อนตั้งศูนย์บัญชาการยังเกิดก่อนงานพักพิงได้ในกระบวนการจริง
    • Phase 0 ปิดขอบเขตและบทบาท; Phase 1–2 พิสูจน์แกนข้อมูล; Phase 3–4 ขยายความสามารถตามเจ้าของงาน; Phase 5 รับรองการใช้งานต่อเนื่องตามขนาดที่ตกลง
    • สิทธิ์ ความปลอดภัย ที่มา และประวัติต้องเริ่มตั้งแต่เก็บข้อมูล ไม่เลื่อนไปทำเฉพาะระยะ production
    • ทุกระยะมี gate หากยังไม่ผ่านให้แก้ข้อบกพร่องหรือปรับขอบเขตที่อนุมัติ ไม่ถือว่าเลื่อนระยะเพราะหน้าจอเสร็จแล้ว

    6.2 ตารางระยะงาน

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    Phase เป้าหมาย ขอบเขตหลัก สิ่งส่งมอบและเงื่อนไขผ่าน
    0 — ยืนยันกระบวนการและ baseline ให้รู้ว่าจะสร้างอะไร ใครใช้ ใครรับรอง ลงทะเบียน Q01–Q08 และปิดข้อที่แพ็กเกจแรกพึ่ง; actor/authority, core data model, privacy, site/device, test plan, integration inventory scope แพ็กเกจแรก รายการ in/out ผังงานและสิทธิ์ dictionary acceptance matrix และ decision log รับรองโดยเจ้าของงาน; ข้อของส่วนขยายมี owner และ gate ก่อนเริ่มส่วนนั้น
    1 — พิสูจน์หน้างานออฟไลน์ บันทึกข้อมูลและยอดได้จริงบนเครื่องที่เตรียมไว้ FM01–FM04 ระดับ slice; CM01–CM02; PRG01/PRG02 ทดลองข้อมูลจำลอง บันทึกผู้มาถึงรวม 10 คน ปิดแอป/รีสตาร์ตเครื่องแล้วข้อมูลและยอดยังอยู่ แก้ยอดมีประวัติ; ไม่ใช้ผลนี้รับรอง sync แล้ว
    2 — เชื่อมทั้งวงจรและ Pilot แกนหลัก หน้างานส่งส่วนกลางและให้ผู้มีสิทธิ์ใช้ข้อมูลได้ sync backend จริง; CM03–CM05, FM05 เริ่มแจ้งเตือนในแอป; PRG03/PRG04 อย่างน้อย 2 เครื่องใน scenario ทดสอบ; retry ไม่ซ้ำ; แก้ conflict/dedup; count/need/last sync ตรง; family outcome ตามสิทธิ์; UAT และแผน fallback
    3A — รับสัญญาณและทรัพยากร เปลี่ยนรายงานและข้อเสนอช่วยเหลือเป็นข้อมูลที่ประเมินได้ XM01–XM03; PRG05; review queue แยกรายงานดิบ/ประมาณ/ยืนยัน; resource card เชื่อมผู้ติดต่อ เงื่อนไข ความพร้อมและ review; ไม่ถือว่า verified = พร้อมรับงาน
    3B — วางแผน ภารกิจ และภาพพื้นที่ เชื่อมข้อมูลกับการตัดสินใจและผลปฏิบัติการ XM04–XM06, XM11; ขยาย PRG02/03/04 snapshot ตาม operational period; ผู้มีอำนาจอนุมัติ; ทีมรับ/ปฏิเสธงานและรายงานกลับ; route/source/staleness; ข่าวสารที่รับรอง
    4 — ส่วนสนับสนุนเฉพาะด้าน เพิ่มบริการที่มีหน่วยงานเจ้าของและนโยบายรองรับ XM07–XM10; PRG06/07 ตรวจรับเป็นแพ็กเกจย่อย: medical referral, inventory/delivery, procurement, relief evidence; แต่ละส่วนมี owner และเกณฑ์ก่อนเปิด
    5 — ใช้งานต่อเนื่องและหลายหน่วยงาน ให้ระบบดูแลต่อและขยายตามปริมาณที่กำหนดได้ hardening, cross-org permissions, approved integrations, migration/archive, support load/security/recovery tests ตาม baseline; deploy/rollback/restore ได้; runbook training และบริการดูแลมีผู้รับช่วง

    Phase 3A/3B เป็นสองส่วนภายใน Phase 3; ระบบข้อมูลร่วมและหน้าที่บางส่วนทำขนานกันได้หลังออก interface และ acceptance baseline แล้ว Phase 4 แต่ละแพ็กเกจอาจเริ่มหลังผ่าน prerequisites ของตัวเอง โดยไม่จำเป็นต้องซื้อครบทุกส่วน ส่วน Phase 5 ใช้กับชุดฟังก์ชันที่ตกลงนำขึ้น production แม้บางทางเลือก Phase 4 ยังไม่ถูกเลือก

    ขอบเขต Pilot แกนหลักยังเป็นหนึ่งจุดปฏิบัติงาน การทดสอบ transfer ใน AT11 ใช้จุดปลายทางที่สองในชุดข้อมูล/สภาพแวดล้อมทดสอบ เพื่อพิสูจน์กฎข้อมูล ไม่ถือว่าอนุมัติขยาย Pilot จริงเป็นสองจุด หากต้องใช้หลายจุดจริงให้รับรอง scope และทรัพยากรเพิ่มก่อน

    6.3 ความสัมพันธ์และลำดับตัดสินใจ

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    งาน ต้องพร้อมก่อน ผลหากยังไม่พร้อม
    Offline intake Q01, Q02, Q04, Q05, Q08 และสิทธิ์เก็บข้อมูล ยังล็อก form/record/count rule ไม่ได้
    Sync และยอดส่วนกลาง identity mapping, event/site scope, revision/idempotency, server acknowledgement ไม่ใช้ UI ออนไลน์เป็นหลักฐานส่งสำเร็จ
    Family Portal Q03, policy ของสถานะ/ผู้ยืนยัน/สิทธิ์/อายุข้อมูล ทดลองเฉพาะข้อมูลจำลอง; ยังไม่เปิดค้นข้อมูลจริง
    Supply/Needs Q06 และหน่วยนับ/สถานะ/ผู้รับผิดชอบ เปรียบเทียบและปิดคำขอจากยอดไม่ได้
    Mission dispatch resource readiness และอำนาจมอบหมาย แสดงข้อเสนอจัดสรรได้ แต่ยังไม่ออกคำสั่งจริง
    Medical referral medical owner, protocol, data access และหน่วยรับส่งต่อ คงเพียง flag ขอความช่วยเหลือ ไม่เปิด workflow ทางการแพทย์จริง
    Procurement/Relief evidence Q07, budget/policy owner, approved process/integration จัดแฟ้มอ้างอิงได้เฉพาะที่อนุญาต; ไม่อนุมัติสิทธิ์/จ่ายเงิน

    ระยะเวลาและงบ: ให้ประมาณแยกแต่ละแพ็กเกจหลัง Phase 0 โดยแจกงาน วิเคราะห์/ออกแบบ พัฒนา เชื่อมต่อ ทดสอบ อบรม และดูแล พร้อม assumptions และงานที่รอหน่วยงานภายนอก ไม่ยกตัวเลข 2 สัปดาห์หรือระยะเวลาใน S073 มาใช้เป็นกำหนดส่งตามสัญญา

    หากเลือก resource-first ใน Q01: เปลี่ยน Phase 1 เป็น XM02–XM03 ระดับ intake→review→resource card และเลื่อน shelter slice ตาม dependency; FM01–FM04 และกฎข้อมูลร่วมยังต้องมีในระดับที่ใช้จริง ให้จัดทำ baseline ฉบับแก้ก่อนเริ่มแพ็กเกจ มิใช่ถือว่าเอกสารเดิมเลือกให้แล้ว

    8. รายละเอียดข้อกำหนดรายโมดูล

    ข้อกำหนดต่อไปนี้เป็นข้อเสนอ TOR โดยแต่ละแพ็กเกจต้องแนบรายละเอียด field/state/role และกรณีทดสอบที่รับรองก่อนเริ่มพัฒนา

    FM01 — ตัวตน องค์กร สิทธิ์ และอำนาจ

    • ความสามารถ: จัดบัญชี องค์กร บทบาท พื้นที่/เหตุการณ์ที่เข้าถึง การมอบสิทธิ์ และการระงับสิทธิ์; แยกผู้ดูแลเทคนิคจากผู้อนุมัติภารกิจและผู้อ่านข้อมูลอ่อนไหว
    • ข้อมูลหลัก: user, organization, role, event/site scope, delegation, session/device, ผู้อนุมัติและระยะเวลาสิทธิ์
    • กฎ/ข้อยกเว้น: ตรวจสิทธิ์ที่ server/API และไฟล์แนบ; ปฏิเสธการข้ามขอบเขต; การใช้งาน offline ต้องกำหนดอายุสิทธิ์และขั้นตอนเมื่อเพิกถอนสิทธิ์ขณะเครื่องยัง offline
    • ตรวจรับ: บัญชีเดียวกันเข้าได้เฉพาะบทบาทที่กำหนด; ทดสอบเรียก API/เปิดไฟล์โดยตรงและเปลี่ยน ID แล้วไม่หลุดขอบเขต; มีประวัติการให้/ยกเลิกสิทธิ์
    • สิ่งส่งมอบ/หลักฐาน: permission matrix, authority/delegation rule, session policy และผล negative tests [S049, D13]

    FM02 — เหตุการณ์และทะเบียนจุดปฏิบัติงาน

    • ความสามารถ: สร้าง/เลือกเหตุการณ์ จุดพักพิง จุดช่วยเหลือ พื้นที่ องค์กรเจ้าของ และผู้รับผิดชอบ; รักษาประวัติการเปลี่ยนแปลง
    • ข้อมูลหลัก: incident ID, site ID, type, name, location, owner, contact, capacity, lifecycle status และเวลา
    • กฎ/ข้อยกเว้น: รหัสภายในไม่เปลี่ยนเมื่อเปลี่ยนชื่อ; แยก lifecycle เช่น active/closed จากสถานะความจุ near capacity/full; จุดที่ปิดยังตรวจประวัติได้
    • ตรวจรับ: บันทึกจากสองเหตุการณ์ไม่ปนกัน; เปลี่ยนชื่อ/ความจุแล้วรายการเดิมยังอ้างถึงจุดที่ถูกต้อง; จุดใหม่ offline เข้าส่วนกลางโดยไม่ชนหรือมีขั้นตอน reconcile
    • สิ่งส่งมอบ/หลักฐาน: site/event schema, lifecycle และ reconciliation cases [S049, S069, S070]

    FM03 — ที่มา คุณภาพข้อมูล ประวัติ หลักฐานและการคุ้มครองข้อมูล

    • ความสามารถ: บันทึกแหล่งข้อมูล ผู้บันทึก เวลาที่เกิด/สังเกต/รับรายงาน ระดับความเชื่อมั่น revision การแก้ไข และการเข้าถึง/ส่งออกตามนโยบาย; จัดสิทธิ์เอกสารแนบเมื่อมีในขอบเขต
    • กฎ/ข้อยกเว้น: ประวัติแก้ไขไม่ถูกแทนที่เงียบ ๆ; แยกรายงานดิบ ข้อมูลประมาณ และข้อมูลที่ตรวจแล้ว; รูปถ่ายและเลขประจำตัวไม่บังคับหากไม่จำเป็นต่อ slice; การลบ/ลดข้อมูลต้องตามนโยบาย retention ที่รับรอง
    • ตรวจรับ: ย้อนจากยอด/สถานะไปหา record และผู้แก้ได้; ป้องกันการแก้ audit ผ่านบัญชีปกติ; แสดงว่าข้อมูลขัดแย้ง/เก่า/ที่มาไม่ครบ; ไฟล์และ export ไม่ข้ามสิทธิ์
    • สิ่งส่งมอบ: data classification, provenance/audit specification, attachment policy, retention และตัวอย่าง export ที่ลดข้อมูลตามสิทธิ์
    • หลักฐาน: [S049, S069, S070] เป็นฐานแนวคิด ไม่ใช่หลักฐานว่าการเข้ารหัสหรือ audit ถูกพัฒนาแล้ว

    FM04 — ออฟไลน์และการซิงก์

    • ความสามารถ: เตรียม app shell และข้อมูลจุดที่จำเป็น; บันทึก local transaction กับ outbox; แสดง pending/syncing/synced/conflict/failed; retry และ reconcile หลายเครื่อง
    • กฎ: ข้อความ “บันทึกแล้ว” หมายถึงบันทึก local สำเร็จ; “ส่งแล้ว” ต้องมี server acknowledgement; retry ใช้ operation ID เดิม; business status แยกจาก sync status
    • ข้อยกเว้น: first use ไม่มีเน็ต, storage เต็ม/ถูกล้าง, version migration, server รับสำเร็จแต่ response หาย, app ถูกปิดระหว่างส่ง, เครื่องหาย และเวลาเครื่องคลาดเคลื่อนต้องมีพฤติกรรมที่ระบุ
    • ตรวจรับ: เตรียมเครื่อง→ปิดเน็ต→บันทึก→ปิดแอปและรีสตาร์ตเครื่อง→เปิดใหม่; ส่งซ้ำ/ขาดสัญญาณกลางทางแล้วไม่เพิ่ม record ซ้ำ; conflict ยังมีข้อมูลต้นทางและผู้ทบทวน
    • สิ่งส่งมอบ/หลักฐาน: sync protocol, operation identity, acknowledgement, conflict rules, offline readiness checklist และ recovery guide [S069, S070, Q05]

    FM05 — แจ้งเตือนและส่งต่อเรื่องเร่งด่วน

    • ความสามารถ: แจ้งในแอปเมื่อมีคำขอเร่งด่วน ข้อมูลค้างหรือภารกิจต้องติดตาม; ตั้งผู้รับ trigger ลำดับ escalation และยืนยันรับทราบ
    • ข้อมูล/สถานะ: notification ID, object ID, recipient, channel, attempt, sent/delivered/acknowledged/failed และเวลา โดยแยกการส่งสำเร็จจากการรับทราบ
    • กฎ/ข้อยกเว้น: ข้อความภายนอก/preview ไม่ใส่ข้อมูลอ่อนไหวเกินนโยบาย; ส่งซ้ำไม่รบกวนไม่จำเป็น; ช่องทางภายนอกล่มต้องแสดง failure และทางติดตามด้วยคน
    • ตรวจรับ: trigger ส่งถึงผู้มีหน้าที่ที่ถูกต้อง; ผู้ใช้ไร้สิทธิ์ไม่เห็น payload; failed ไม่แสดงว่าเจ้าหน้าที่รับทราบแล้ว; gateway mock ไม่ใช้แทนผล live integration
    • สิ่งส่งมอบ/หลักฐาน: notification/escalation matrix และ delivery logs [S049]; SMS/LINE/email/push ภายนอกเป็นทางเลือกในข้อ 11

    CM01 — ลงทะเบียนผู้มาถึงและทะเบียนคน ณ จุดพักพิง

    • ความสามารถ: เริ่มจากกลุ่มคนที่มาถึงจริง; เลือกเหตุการณ์/จุด; ระบุจำนวนและข้อมูลขั้นต่ำ; เติมข้อมูลรายบุคคลภายหลัง; แก้ข้อมูลด้วย revision; ให้รหัสอ้างอิงตาม Q02
    • ข้อมูลขั้นต่ำที่เสนอสำหรับ slice: registration group, site/event, total present, age-group breakdown ถ้าทราบ, officer/device และเวลา; ชื่อ เบอร์ บัตร และความสัมพันธ์ครัวเรือนเก็บเมื่อมีเหตุจำเป็นและนโยบายรองรับ
    • กฎ: กลุ่มผู้มาด้วยกันไม่เท่ากับครัวเรือน; ไม่มีบัตร/มือถือ/วันเกิดไม่ขัดขวางการบันทึกขั้นต่ำ; สถานะลงทะเบียนไม่เท่ากับ safe; flag ขอแพทย์ไม่ใช่การวินิจฉัย
    • ข้อยกเว้น/ตรวจรับ: ข้อมูลไม่ครบยังบันทึกได้; unknown age ไม่ถูกแต่งเป็นข้อมูลจริง; เติมรายบุคคลแล้วไม่เพิ่มยอดซ้ำ; possible duplicate ให้บันทึกได้พร้อมคิว review
    • สิ่งส่งมอบ/หลักฐาน: intake form/states, minimum-data rule, group→person linkage และ revision cases [D01, S067, S069, S070, Q02/Q04]

    CM02 — จำนวนคน ความจุ และการย้าย

    • ความสามารถ: แสดงจำนวนที่อยู่ปัจจุบัน ยอดรับเข้า/ออก/ย้าย ความจุ และสถานะใกล้เต็ม/เต็ม พร้อมแยกประมาณจากยืนยัน
    • กฎ: กำหนด record ที่เป็นฐานยอดเพียงชุดเดียว; รายบุคคลที่เพิ่มให้กลุ่มเดิมต้องไม่บวกซ้ำ; การย้ายต้องเชื่อมออกต้นทาง/รับปลายทางและสถานะระหว่างทาง; การแก้ยอดต้องมีเหตุผล/ผู้รับรอง
    • ข้อยกเว้น: duplicate ข้ามเครื่อง ผู้ย้ายยังไม่ถึงปลายทาง ความจุเปลี่ยน ไม่ทราบอายุ และศูนย์ไม่ส่งข้อมูล; ห้ามสรุปจำนวนคนทั้งเหตุการณ์ว่าไม่ซ้ำหาก dedup ระหว่างจุดยังพิสูจน์ไม่ได้
    • ตรวจรับ: fixture ที่รู้ยอดให้ผลตรงก่อน/หลัง sync; รับ 10 คน แก้กลุ่ม เติมคนในกลุ่ม และย้ายแล้วไม่บวกซ้ำ; แสดงสถานะ provisional หรือ unresolved เมื่อยังตัดสินความซ้ำไม่ได้
    • สิ่งส่งมอบ/หลักฐาน: counting policy, transfer model, dedup review และ expected-total fixtures [D03, Q04, S069/S070]

    CM03 — ของคงเหลือโดยประมาณและคำขอ

    • ความสามารถ: บันทึก snapshot น้ำ/อาหาร/พื้นที่ ณ จุด พร้อมหน่วย เวลา ผู้รายงาน และฐานประมาณการ; สร้างคำขอระบุชนิด จำนวน หน่วย ความเร่งด่วนและเจ้าของ
    • สถานะคำขอที่เสนอ: requested→acknowledged→preparing→dispatched→completed; cancelled เมื่อผู้มีสิทธิ์ยกเลิก; การรับบางส่วนต้องแสดง requested/received/outstanding แยกกัน
    • กฎ/ข้อยกเว้น: “น้ำเหลือ 8 ชั่วโมง” เป็นการประมาณพร้อมฐานคำนวณ มิใช่ stock ledger; unknown ไม่เท่ากับ 0; dispatch ไม่เท่ากับได้รับของ; การลดคำขอ/รับบางส่วนมีประวัติ
    • ตรวจรับ: ขอ 200 ขวด ส่ง 120 รับจริง 100 แล้วแสดงยอดตามความหมายแต่ละขั้น ไม่ปิดครบอัตโนมัติ; ใช้หน่วยต่างกันไม่รวมโดยไม่มี conversion ที่รับรอง
    • สิ่งส่งมอบ/หลักฐาน: unit dictionary, supply snapshot form, need workflow และ fulfillment cases [D04, Q06, S069/S070]

    CM04 — ภาพสถานการณ์ส่วนกลาง รายงานและส่งต่อเวร

    • ความสามารถ: สรุปคน ความจุ กลุ่มที่ต้องดูแล ของขาด คำขอ และสถานะส่งข้อมูลตามขอบเขต; filter เหตุการณ์/พื้นที่/ช่วงเวลา; export รายงานและ handover เรื่องค้าง
    • กฎ: ทุกยอดมี source/as-of/ระดับประมาณหรือยืนยัน; last sync แยกจาก observed time; ส่วนกลางที่ติดต่อเครื่องไม่ได้ไม่อ้างว่ารู้คิว unsent ปัจจุบันทั้งหมด
    • ข้อยกเว้น: ข้อมูลเก่า ติดขัด ขัดแย้ง หรือยังไม่เคยส่ง; แยก “ไม่มีข้อมูล” จาก “ไม่มีคน/ไม่มีความต้องการ”; จำกัดแถวและข้อมูล export ตามสิทธิ์
    • ตรวจรับ: ยอดตรง fixture และรายการที่ server รับ; ข้อมูลก่อน/หลัง sync แสดงเวลาและที่มา; export/handover ตรงข้อมูล ณ snapshot และมีประวัติส่งออก
    • สิ่งส่งมอบ/หลักฐาน: indicator definitions, dashboard/report pack, freshness rules, handover template [D05, S049/S069/S070/S075]

    CM05 — สถานะสำหรับครอบครัว

    • ความสามารถ: รับคำขอค้น/ยืนยันตามช่องทางที่รับรอง; แสดง found/possible match/pending review/not found และ safety status ที่มีผู้ยืนยันตามสิทธิ์
    • กฎ: ผลใกล้เคียงยังไม่เป็นการยืนยันคนเดียวกัน; check-in ยังไม่เป็น safe; not found ไม่สรุปว่าเสียชีวิต/สูญหาย/ไม่เคยได้รับช่วย; แสดงเวลาที่สถานะอ้างถึงและข้อจำกัดการ sync
    • สิทธิ์/ข้อยกเว้น: นโยบายผู้ค้นและการยืนยันความสัมพันธ์ต้องเลือกใน Q03; ไม่เปิดพิกัดละเอียด เลขบัตร เบอร์ หรือข้อมูลการแพทย์โดยอัตโนมัติ; จำกัดการไล่ค้นและบันทึกเหตุผิดปกติ
    • ตรวจรับ: fixture ของทุก outcome รวมชื่อซ้ำ ผู้ไร้สิทธิ์ ศูนย์ยังไม่ส่ง และสถานะเก่า; API/ไฟล์/export ไม่คืนข้อมูลเกินนโยบาย; ผู้ไม่มีสิทธิ์เปลี่ยน safety status ไม่สำเร็จ
    • สิ่งส่งมอบ/หลักฐาน: search/verification policy, response matrix, safety-state transition authority และ abuse tests [D06, Q03, S069/S070]

    XM01 — รับสัญญาณและประเมินภาระการดูแล

    • ความสามารถ: รับแจ้งด้วยคน/web และช่องทางที่ตกลง; เก็บ raw signal, location confidence, reported count, vulnerability/need; review ความซ้ำ; สร้าง care-load snapshot
    • กฎ: แยกจำนวนข้อความ จำนวนกลุ่ม และจำนวนคน; raw signal ไม่บวกเป็น headcount จริง; source/time/confidence และวิธีรวมต้องแสดง; ประมาณการมีเจ้าของและรุ่น
    • ข้อยกเว้น/ตรวจรับ: หลายช่องทางแจ้งคนกลุ่มเดียวกันต้องมี trace และ unresolved flag; รายงานขัดกันยังเก็บต้นฉบับ; USSD simulator ผ่านได้เฉพาะเกณฑ์ simulator ไม่ยืนยันว่าเชื่อม operator แล้ว
    • สิ่งส่งมอบ: channel contract, raw→reviewed→snapshot model และ dedup fixtures
    • หลักฐาน/เงื่อนไข: [D07, S024, S041, S073]; live USSD/SMS รอข้อ 11

    XM02 — รับผู้ช่วย ทีม อุปกรณ์ และสิ่งสนับสนุน

    • ความสามารถ: intake type บุคคล ทีม/องค์กร อุปกรณ์ supply lot และ bulk import ที่เลือก; เก็บ capability ปริมาณ หน่วย ที่ตั้ง ETA ผู้ติดต่อ และข้อจำกัดก่อนเริ่มช่วย
    • กฎ: แยกผู้เสนอ resource จากตัว resource และสิทธิ์ให้มอบหมาย; ข้อมูลขั้นต่ำตาม type; import ต้องมี preview ตรวจ field/duplicate และแจ้งแถวผิด ไม่ผ่านทั้งไฟล์เงียบ ๆ
    • ข้อยกเว้น/ตรวจรับ: บุคคลอยู่หลายทีม/ทรัพยากรถูกเสนอซ้ำ/ยังไม่ทราบ ETA; resource card ย้อนถึง intake ได้; import ซ้ำตาม policy ไม่ทำให้ capacity ซ้ำ
    • สิ่งส่งมอบ: intake schemas, forms/resource cards, import template และ error report
    • หลักฐาน: [D08, S038, S044, S073]; support lot ในระยะนี้เป็นข้อเสนอสิ่งสนับสนุน มิใช่การรับเข้าคลังจริง

    XM03 — ตรวจทรัพยากร ความพร้อม และเงื่อนไขก่อนใช้งาน

    • ความสามารถ: คิว coordinator review, verified/needs more info/rejected; แสดง readiness, availability, staging, สิ่งที่ต้องมีเพื่อเริ่มงาน และผลการตรวจ
    • กฎ: verification และ readiness เป็นคนละสถานะ; assignment ต้องตาม availability/permission; resource ที่จองให้ภารกิจอื่นแล้วไม่เป็นพร้อมเต็มจำนวน
    • ข้อยกเว้น/ตรวจรับ: ยกเลิกความพร้อมหลัง review หรือส่วนติดต่อขาด; ย้อนเหตุผลและผู้ตรวจได้; สถานะ stale ไม่แสดงเป็นพร้อมทันที; ไม่มอบหมายเกิน capacity ที่กำหนด
    • สิ่งส่งมอบ: review/readiness state model, coordinator board และ resource reservation policy
    • หลักฐาน: [D08, S046/S058, S073]

    XM04 — วางแผน เป้าหมาย และบันทึกการตัดสินใจ

    • ความสามารถ: สร้าง snapshot สถานการณ์ ทรัพยากร ข้อจำกัด ช่องว่างข้อมูล และเรื่องรอตัดสินใจสำหรับ operational period; บันทึกเป้าหมาย กลยุทธ์ ลำดับสำคัญ ผู้อนุมัติ และเหตุผล
    • กฎ: snapshot คงหลักฐานที่ใช้ในขณะตัดสินใจ; เป้าหมายและคำสั่งจริงต้องมีผู้มีอำนาจ; เวอร์ชันใหม่ไม่เปลี่ยนบันทึกเก่า; ข้อมูลที่ยังขาดแสดงว่าไม่เก็บ/เข้าไม่ถึง/ใช้ไม่ได้/ประมาณ
    • ข้อยกเว้น/ตรวจรับ: เปลี่ยนแผนกลางรอบ มี conflicting report หรือข้อมูลเก่า; ย้อน decision→source→mission ได้; บัญชีผู้ดูข้อมูลอนุมัติคำสั่งไม่ได้
    • สิ่งส่งมอบ: planning/decision workflow, snapshot model, authority matrix และ template ที่หน่วยงานรับรอง
    • หลักฐาน: [S050/S072/S073, D09]; การสร้าง IAP/แบบฟอร์ม ICS ครบชุดเป็นทางเลือกเมื่อระบุรายการและ owner จริง

    XM05 — ภารกิจและรายงานภาคสนาม

    • ความสามารถ: แปลงคำขอ/เป้าหมายเป็น mission; เสนอทีม/ทรัพยากร; อนุมัติ มอบหมาย รับ/ปฏิเสธงาน อัปเดตและส่งผล offline ตามสิทธิ์; รองรับ Scout/Damage & Needs Assessment เป็นแบบรายงานย่อยเมื่อเลือกขอบเขตสำรวจ
    • สถานะที่เสนอ: draft→approved→assigned→accepted→in progress→reported→closed; rejected/cancelled/blocked ต้องมีเหตุผลและผู้มีสิทธิ์
    • กฎ: ระบบสนับสนุนการตัดสินใจ ผู้มีอำนาจเป็นผู้สั่งการ; field report ที่ส่งซ้ำไม่ปิด mission ซ้ำ; completion report ต่างจากผลที่ reviewer รับรอง; ปลด resource ตามนโยบายจริง
    • ตรวจรับ: เดิน flow ครบหนึ่งภารกิจรวมทีมปฏิเสธ งานติดขัด และรายงาน offline; อัปเดตได้เฉพาะทีม/ผู้มีสิทธิ์; handover เห็นงานค้างและเวอร์ชันคำสั่ง
    • สิ่งส่งมอบ/หลักฐาน: dispatch workflow, mission card, field report, scout assessment ที่เลือก และ completion/exception tests [D09, S049/S071/S073]

    XM06 — แผนที่ เส้นทาง และสถานะโครงสร้างพื้นฐาน

    • ความสามารถ: แสดงจุด คำขอ ภารกิจ พื้นที่เสี่ยง เส้นทาง และสถานะถนน ไฟฟ้า น้ำ สื่อสาร/สุขาภิบาลตาม layers ที่เลือก; ดู confidence/source/as-of และข้อจำกัดการเข้าถึง; รองรับ Pre-setup Checklist ก่อนเปิดจุด เช่น รถเข้าถึง ไฟ น้ำ สัญญาณ ห้องน้ำ พื้นที่แยกและความจุ เมื่อหน่วยงานเลือกใช้
    • กฎ: แยกข้อมูลอ้างอิงและข้อมูลหน้างาน; route suggestion ไม่รับรองว่าเส้นทางปลอดภัย; จำกัด layers และพิกัดอ่อนไหว; พิกัด unknown ไม่แปลงเป็นจุดจริง
    • ข้อยกเว้น/ตรวจรับ: map provider ล่ม/ไม่มี GPS/ข้อมูลชั้นเก่า; ยังเห็นรายการและคำอธิบายสถานที่ที่จำเป็น; layers มี provenance; ไม่เปิดข้อมูลข้ามสิทธิ์
    • สิ่งส่งมอบ: layer/source inventory, map/list fallback, pre-setup assessment ที่เลือก และ route/location confidence policy; ผล checklist เป็นข้อมูลให้ผู้รับผิดชอบประเมิน มิใช่ระบบรับรองพื้นที่ปลอดภัยอัตโนมัติ
    • หลักฐาน/ขอบเขต: [D09, S049/S071/S075]; mesh/satellite/generator ใน blueprint เป็น infrastructure dependency การจัดซื้อหรือควบคุมอุปกรณ์จริงต้องเป็นแพ็กเกจแยก

    XM07 — ประสานการแพทย์และส่งต่อ

    • ความสามารถ: บันทึกคำขอการช่วยเหลือ/ส่งต่อ ผู้ประสาน ปลายทางตอบรับ สถานะการเคลื่อนย้าย และหลักฐานรับต่อ ตาม protocol ที่ผู้รับผิดชอบกำหนด
    • กฎ: clinical assessment/triage เป็นหน้าที่ผู้ได้รับมอบหมาย; flag บาดเจ็บใน MVP ไม่ใช้แทนการประเมิน; ความพร้อมปลายทางต้องมีเวลาและผู้รับรอง; ไม่ปิดส่งต่อจากสถานะรถออกเพียงอย่างเดียว
    • ข้อยกเว้น/ตรวจรับ: ปลายทางไม่รับ เปลี่ยนปลายทาง สื่อสารขาด และข้อมูลคนไม่ครบ; scenario ต้องผ่านผู้ปฏิบัติการแพทย์; ทดสอบสิทธิ์ข้อมูลและการตอบรับทั้งสองฝ่าย
    • สิ่งส่งมอบ: approved referral protocol/data set, responsibility matrix และ handoff tests
    • หลักฐาน/เงื่อนไข: [D10, S073/S075]; เริ่มเมื่อมี medical owner/หน่วยรับส่งต่อ ไม่รวมเวชระเบียนเต็มหรือการตัดสินใจรักษาอัตโนมัติ

    XM08 — คลัง บริจาค ขนส่ง และรับมอบ

    • ความสามารถ: เปลี่ยนข้อเสนอสิ่งสนับสนุนเป็น lot ที่รับจริง; บันทึกหน่วย สถานที่ สภาพ/วันหมดอายุเมื่อเกี่ยวข้อง; รับเข้า จอง จ่าย โอน ส่ง รับบางส่วน คืน/เสียหาย และหลักฐานรับมอบ
    • กฎ: stock ledger ต่างจาก CM03 supply snapshot; offered ไม่เท่ากับ received; quantity/unit/conversion ชัด; ห้ามมี ledger operation ซ้ำจาก retry; การปรับยอดมีผู้รับรอง
    • ข้อยกเว้น/ตรวจรับ: รับไม่ครบ ขนส่งผิดจุด ของหมดอายุ/เสียหาย และหน่วยต่างกัน; test fixture รับ→จ่าย→คืน→โอนแล้ว balance ตรงและ trace ถึงคำขอ
    • สิ่งส่งมอบ: inventory/lot model, receiving/delivery workflow, unit master และ reconciliation tests
    • หลักฐาน/ทางเลือก: [D11, S038/S073/S075]; Catering เพิ่ม meal demand/แจกจ่าย/ของเสียได้เมื่อมี owner; ไม่เพิ่มระบบเมนู/โภชนาการเต็มโดยอัตโนมัติ

    XM09 — คำขอจัดซื้อ ผู้สนับสนุน และหลักฐานค่าใช้จ่าย

    • ความสามารถ: เชื่อม demand กับคำขอจัดซื้อ ผู้รับผิดชอบงบ vendor/partner การอนุมัติ หลักฐานส่งมอบ และสถานะค่าใช้จ่ายตามขั้นตอนเจ้าของงบ
    • กฎ: การเสนอจัดซื้อไม่เท่ากับอนุมัติ; ผู้มีอำนาจและลำดับอนุมัติต้องกำหนดก่อน; audit ตั้งแต่สร้างคำขอ; งานนี้ไม่ทำให้การจัดซื้อถูกต้องตามระเบียบโดยอัตโนมัติ
    • ข้อยกเว้น/ตรวจรับ: เปลี่ยนยอด อนุมัติบางส่วน ยกเลิก และส่งมอบไม่ครบ; ทดสอบผู้ไร้อำนาจอนุมัติไม่ได้; หลักฐานเชื่อม request→approval→delivery ได้
    • สิ่งส่งมอบ: owner-approved procurement workflow, authority/amount rules และ evidence/export pack
    • หลักฐาน/เงื่อนไข: [D12, S073]; ไม่ยกตัวเลขจาก fiscal mock data เป็นงบหรือรายการใช้จ่ายจริง

    XM10 — แฟ้มหลักฐานช่วยเหลือและประกัน

    • ความสามารถ: จัดแฟ้มข้อมูลเหตุการณ์ การลงทะเบียน และหลักฐานที่หน่วยงานอนุญาตให้ใช้ประกอบการพิจารณา; ส่งออก/ส่งต่อ/ติดตามตาม interface ที่ตกลง
    • กฎ: check-in เป็นหลักฐานหนึ่งรายการ ไม่รับรองสิทธิ์เงินช่วยเหลือหรือเคลมประกัน; ข้อมูลที่ส่งต้องมี purpose/recipient/permission และประวัติ; แยกสถานะส่งแฟ้มจากผลพิจารณาภายนอก
    • ข้อยกเว้น/ตรวจรับ: ผู้รับปฏิเสธแฟ้ม/หลักฐานไม่ครบ/ติดต่อระบบภายนอกไม่ได้; ไม่มี response ไม่แสดงอนุมัติ; ผู้ไม่มีสิทธิ์ไม่ส่งออกข้อมูลรายบุคคล
    • สิ่งส่งมอบ: evidence requirement matrix, approved handoff/API contract และ response state model
    • หลักฐาน/เงื่อนไข: [D12, Q07, S077]; เป็นทางเลือกจนมีหน่วยงานเจ้าของเกณฑ์และข้อตกลงใช้งาน

    XM11 — ข้อมูลสาธารณะที่รับรอง

    • ความสามารถ: จัดทำ ทบทวน อนุมัติ เผยแพร่ แก้ไข และหมดอายุข้อความสถานการณ์/คำแนะนำ/จุดบริการ ตามผู้รับผิดชอบการสื่อสาร
    • กฎ: ข้อความสาธารณะอ้างถึงเหตุการณ์ เวลา แหล่งที่มา ผู้อนุมัติและรุ่น; ไม่ดึงรายงานดิบหรือข้อมูลคนไปเผยแพร่อัตโนมัติ; เก็บประวัติการแก้ไข
    • ข้อยกเว้น/ตรวจรับ: ข่าวเก่า คำแนะนำเปลี่ยน ช่องทางส่งล้มเหลว; draft ไม่เผยแพร่; expired มีการแสดงสถานะที่ตกลง; gateway แต่ละช่องทางมีผลส่งตรวจได้
    • สิ่งส่งมอบ: public-message workflow, content/approval/expiry policy และ publish tests
    • หลักฐาน: [S072/S073]; เว็บไซต์ portfolio เดิมใช้เล่าโครงการ ไม่ใช้แทนแหล่งประกาศปฏิบัติการที่รับรอง

    9. แบบข้อมูลและกฎที่ใช้ร่วมกัน

    9.1 Entity หลักที่ต้องออกแบบ

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    กลุ่ม Entity จุดที่ต้องแยก
    อำนาจและขอบเขต User, Organization, Role, Delegation, Incident, Site, Device org role ต่างจากอำนาจสั่งการ; เหตุการณ์ต่างจากปีงบ
    คนและการอยู่ ณ จุด Registration Group, Person, Household, Check-in/Stay, Transfer กลุ่มที่มาด้วยกันต่างจากครัวเรือน; คนต่างจากจำนวน check-in
    คำยืนยันสถานะคน Safety Assertion/Status Verification เชื่อม person/record, status, verifier/authority, evidence/source, observed/effective/recorded time, revision/revocation และ visibility; แยกจากการอยู่ ณ จุด
    ทรัพยากร/คำขอ Supply Snapshot, Need Request, Fulfillment, Resource, Resource Offer/Review ของประมาณต่างจาก stock ledger; คำขอต่างจากได้รับแล้ว
    การส่งข้อมูล Local Operation, Revision, Sync Batch, Server Receipt, Conflict/Dedup Case retry ต่างจากธุรกรรมใหม่; conflict ต่างจาก failed
    ข้อมูลสถานการณ์ Raw Signal, Reviewed Observation, Care-load/Situation Snapshot, Map Layer reported count ต่างจาก verified count
    การทำงาน Objective, Operational Period, Decision, Mission, Field Report รายงานผลต่างจากผู้รับรองปิดงาน
    ส่วนขยาย Referral, Inventory Lot/Movement, Delivery Receipt, Procurement Request, Evidence Case ส่งต่อ/ส่งแฟ้มต่างจากรับสำเร็จ/อนุมัติ
    ประวัติ/การสื่อสาร Audit Event, Attachment, Export, Notification, Public Message sent ต่างจาก delivered/acknowledged

    ตารางนี้เป็น conceptual model มิใช่ SQL schema สำเร็จ ใน Phase 0 ต้องกำหนด cardinality, required fields, null/unknown, ownership, index และกฎแก้ไขเฉพาะแกนข้อมูลร่วมกับแพ็กเกจแรก ส่วนรายละเอียด Entity ของแพ็กเกจขยายให้รับรองก่อนเริ่มแพ็กเกจนั้น โดยไม่ขัด interface และกฎร่วมที่ตกลงไว้

    9.2 กฎร่วมที่ต้องพิสูจน์

    1. ใช้รหัสข้อมูลภายในที่ไม่ชนระหว่างเครื่อง และแยกรหัสอ้างอิงสำหรับคน/เจ้าหน้าที่จาก primary identity
    2. การบันทึก local และ outbox ต้องสัมพันธ์กัน ไม่แสดงสำเร็จขณะที่รายการไม่มีคิวส่งหรือไม่ได้บันทึก
    3. เติมข้อมูล person ให้ group เดิมต้องมี linkage และวิธีนับที่ไม่บวกจำนวนซ้ำ; ถ้าทำ dedup ไม่ได้ให้แสดงยอดประมาณ/รอ review
    4. เก็บ source, actor, event/site, revision และเวลาสำคัญ; เก็บ timezone/เวลา server receipt แยกจากเวลาตามเครื่อง
    5. unknown, not collected, not applicable และ 0 เป็นคนละความหมาย
    6. แยกสถานะธุรกิจ สถานะตรวจสอบ สถานะความพร้อม สถานะส่งข้อมูล และสถานะข้อมูลเก่า
    7. ทุก transition ที่มีผลต่อ safe, จำนวนคน, mission, stock หรือ approval ต้องมีผู้มีสิทธิ์และเหตุผลตามกฎ
    8. เกณฑ์ข้อมูลเก่าและการอนุมานต้องกำหนดต่อ domain ไม่มีค่า freshness ค่าเดียวสำหรับทุกข้อมูล

    10. ข้อกำหนดด้านคุณภาพและบริการเบื้องหลัง

    10.1 การใช้งาน

    รองรับภาษาไทย ใช้หน้าจอที่อ่านง่ายบนอุปกรณ์จริงที่เลือก ฟอร์มไม่ต้องพึ่งสีเพียงอย่างเดียว สถานะ local/ส่วนกลางชัด มีข้อความบอกผลและวิธีกลับมาทำงานเมื่อผิดพลาด ผู้ใช้งานต้องผ่าน task-based UAT ตามบทบาท ไม่ใช้คำว่า “ไม่ต้องอบรม” เป็นข้อเท็จจริงจาก demo

    การรองรับ Android/iOS/browser และรุ่นขั้นต่ำต้องระบุใน device/browser matrix หลังสำรวจอุปกรณ์ ความสามารถ offline ของแต่ละแพลตฟอร์มต้องทดสอบบนชุดนั้นก่อนรับรอง

    10.2 ความปลอดภัยและข้อมูล

    ตรวจสิทธิ์ที่ backend/API ไฟล์แนบและ export; ใช้การสื่อสารที่ป้องกันการอ่านระหว่างทาง; ไม่เก็บ secret ใน client/log; กำหนด app/session lock และ MFA ตามบทบาท; ออกแบบ local data/key protection พร้อมขอบเขตเมื่อเครื่องหาย/ถูกล้าง/สิทธิ์ถูกเพิกถอนขณะ offline

    ต้องมีแผน minimization, retention, ลดข้อมูลในเครื่องหลังส่งเมื่อเหมาะสม, response ต่อเครื่องหาย และการอนุญาตใช้ข้อมูลจริงที่เจ้าของข้อมูลรับรอง การเป็น PWA หรือใช้ IndexedDB ไม่ได้ทำให้ข้อมูลในเครื่องเข้ารหัสโดยอัตโนมัติ ต้องออก protection/key/session-lock policy ตาม threat model และพิสูจน์ control ที่เลือกบนอุปกรณ์จริง ไม่อ้างว่า remote wipe หรือเพิกถอนสิทธิ์มีผลทันทีบนเครื่องที่ยัง offline

    Retention matrix ต้องระบุ local/server/files/exports/backups รวมเหตุผลข้อยกเว้น อายุสำเนา ผู้รับผิดชอบ และวิธีลด/ลบตามนโยบายที่รับรอง แยกสิ่งที่ระบบควบคุมได้จากสำเนาที่ส่งให้หน่วยงานอื่นและต้องอาศัยกระบวนการของผู้รับ

    10.3 ความถูกต้อง ความทนทาน และการดูแล

    มี fixtures ตรวจยอด/สถานะ, idempotency/reconciliation, error monitoring, backup และ restore ที่ทดลองได้; มี schema/app-version migration; deploy/rollback และ runbook ส่งต่อทีมดูแล แยก environment ทดลองกับที่ใช้จริง

    ผลแจ้ง online ต้องอ้างอิงการเชื่อมต่อที่ตรวจได้; ผล sync ต้องอ้างอิง server receipt มิใช่ timer; monitoring ที่ส่วนกลางต้องบอกขอบเขตสิ่งที่รู้และสิ่งที่เครื่อง offline ยังไม่ส่ง

    10.4 ตัวเลขคุณภาพที่ต้องกำหนดก่อนตรึงราคา/เริ่มงาน

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    ตัวแปร สิ่งที่ต้องตกลง วิธีพิสูจน์
    Local save time percentile/เวลาสูงสุดบนรุ่นอุปกรณ์ที่เลือกและปริมาณข้อมูลกำหนด วัดจากกดบันทึกถึง transaction สำเร็จจริง
    Offline capacity records/media ต่อเครื่องและช่วงเวลาที่ต้องอยู่ offline ทดสอบข้อมูลตามขนาดพร้อม storage-pressure cases
    Sync performance ขนาด batch, bandwidth/latency, backlog และเวลาที่รับทั้งหมด network-conditioned test และตรวจ server receipts
    Dashboard freshness อายุข้อมูลที่ยอมรับ per domain และ refresh หลัง server รับ เปรียบเทียบ observed/received/rendered timestamps
    Load concurrent users, events/sites, daily operations และ peak profile load test พร้อมรายงาน response/error/resource usage
    Availability/recovery service window, downtime, RPO/RTO และ backup interval incident simulation และ restore rehearsal
    Support severity, response/resolution, service hours และ escalation ตารางบริการและ incident records ตามสัญญา

    ไม่กำหนด SLA/จำนวนผู้ใช้/ความจุจากการคาดเดา ค่าตารางนี้ต้องถูกเติมและรับรองใน baseline ของแพ็กเกจที่เกี่ยวข้อง มิฉะนั้นยังเปรียบเทียบราคาและตรวจรับคุณภาพส่วนนั้นไม่ได้

    11. การเชื่อมต่อระบบภายนอก

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    Interface ขอบเขตที่เสนอ สิ่งที่ต้องมี การตรวจรับ
    Field↔Backend↔Dashboard แกนระบบของ Phase 2 API/schema, operation identity, auth และ acknowledgements ข้อมูลใหม่จาก field ไปถึงส่วนกลางจริง พร้อม retry/conflict
    Identity provider/SSO ทางเลือกเมื่อมีหลายองค์กร IdP owner/protocol/claim mapping/role authority sandbox/production ตาม agreement; ไม่ใช้ account mock แทน
    SMS/USSD ช่องทางรับสัญญาณหรือแจ้งเตือนระยะขยาย operator/provider, channel code, consent/policy, quota/cost และ fallback end-to-end กับ provider; แยก simulator results
    LINE/email/push ทางเลือกแจ้งเตือน channel owner/token, payload policy, delivery semantics ส่ง/ล้มเหลว/รับทราบตามขอบเขตที่ provider ตรวจได้
    Map/GIS/ข้อมูลสภาพพื้นที่ layers ที่เลือก license/source, recency, coordinate system และ outage behavior source-to-layer mapping พร้อม unavailable/stale cases
    โรงพยาบาล/EMS ทางเลือกการประสานส่งต่อ protocol owner, accepted data, receiving workflow และ access มีผลตอบรับจากหน่วยรับ; mock และจริงแยกกัน
    ทะเบียนราษฎร์/แหล่งยืนยันบุคคล ทางเลือกนอก MVP การอนุญาตและ data contract จริง ข้อมูลและสิทธิ์ตามข้อตกลง; ไม่มีข้อตกลงยังไม่รวม live integration
    งบ/เงินช่วยเหลือ/ประกัน ทางเลือกเชื่อมแฟ้ม/ผลพิจารณา owner/criteria/API/authority/privacy สถานะส่งแฟ้มและสถานะตอบจากภายนอกแยกกัน

    ไม่มีหลักฐานในคลังที่เพียงพอให้รับรองว่าการเชื่อมทุกหน่วยงานเกิดขึ้นแล้ว ให้ระบุเจ้าของ interface, endpoint, version, test environment, ค่าใช้บริการและคนจัดการบัญชีใน integration inventory ก่อนจ้างส่วนเชื่อมต่อ

    Interface contract ขั้นต่ำต้องมี payload/schema/version mapping, timeout/retry/rate limit, idempotency/correlation, delivery/acknowledgement semantics, partial/invalid responses, expected state เมื่อปลายทางล่ม, owner/escalation และ fallback การยืนยันว่าได้รับ payload ไม่เท่ากับผู้รับดำเนินงานหรืออนุมัติแล้ว

    12. สิ่งส่งมอบและแพ็กเกจงาน

    12.1 สิ่งส่งมอบขั้นต่ำ

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    ระยะ สิ่งส่งมอบ
    Phase 0 baseline scope/in-out, actor/process/state/exception, authority/permission matrix, decision register, conceptual/data dictionary, architecture/options, integration inventory, estimation assumptions และ acceptance matrix
    Phase 1 runnable offline slice, source/build guide, local data/outbox/revision model, prepared-device guide, fixtures และผล reopen/restart/storage/error tests
    Phase 2 API/database/migrations, sync/conflict/dedup, dashboard/need/family policy implementation, logs, end-to-end/security/UAT reports, backup/restore/fallback และ pilot guide
    Phase 3 intake/review/resource card, signal/snapshot rules, planning/mission/GIS/public-info ที่เลือก, authority/workflow และ tests ตามแพ็กเกจ
    Phase 4 approved domain workflows, data contracts, receiving/stock/referral/procurement/evidence tests, manuals และ interface results เฉพาะส่วนที่จ้าง
    Phase 5 production deployment, migration/recovery/rollback evidence, agreed load/security results, training/admin/operator guides, runbook, dependency/licenses และ support handover

    ทุก release ต้องมี version, รายการ requirement ที่ครอบคลุม, known limitations, test environment/device/data, ผลผ่าน/ไม่ผ่าน และ issue ที่ยังค้าง ข้อมูลตัวอย่างต้องแยกจากข้อมูลจริงอย่างชัดเจน

    แพ็กเกจ โมดูล/งานหลัก จุดตรวจรับ
    PKG00 — วิเคราะห์และออก baseline Phase 0 และ D13 เอกสารและเกณฑ์ผ่านก่อนพัฒนา
    PKG01 — แกนข้อมูลและ Field Offline FM01–FM04, CM01–CM02 local persistence/count/privacy ตาม Phase 1
    PKG02 — MVP เชื่อมส่วนกลาง CM03–CM05, FM04 backend, FM05 in-app end-to-end multi-device และ UAT ตาม Phase 2
    PKG03 — Signals/Resource Intake XM01–XM03 signal provenance/review/readiness/import
    PKG04 — Planning/Operations XM04–XM06, XM11 ถ้าเลือก authorized decisions→missions→field outcomes
    PKG05 — Logistics XM08 receiving/allocation/delivery/stock reconciliation
    PKG06 — Medical Coordination XM07 approved referral/handoff/access

    แพ็กเกจเป็นข้อเสนอแยกงาน ไม่ใช่การกำหนดผู้รับจ้างหรือหน่วยงานผู้ซื้อ การแยกหลายทีมต้องมี data/API/event ID/authority/acceptance owner ร่วมกันก่อน เพื่อลดการสร้างทะเบียนและยอดที่ไม่เชื่อมกัน งานฐานที่ใช้ซ้ำคิดราคาและความรับผิดชอบให้ชัด ไม่คิดพัฒนาใหม่ทุกแพ็กเกจโดยไม่มีเหตุผล

    13. การตรวจรับและหลักฐานทดสอบ

    13.1 กรณีหลักของ Phase 1–2

    ตัวเลข 10 คน, น้ำ 8 ชั่วโมง และคำขอ 200 ขวดใช้เป็น scenario ตัวอย่างจากฐาน MVP ไม่ใช่ capacity/SLA หรือผลทดสอบที่ทำแล้ว จำนวนอย่างน้อย 2 เครื่องและกรณี failure ต่อไปนี้เป็นเกณฑ์ที่เสนอเพิ่มเพื่อพิสูจน์ความน่าเชื่อถือ

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    Test ID กรณี ผลที่คาดและหลักฐาน Gate
    AT01 เตรียมเครื่อง เลือกเหตุการณ์/จุด ปิดอินเทอร์เน็ต app shell และข้อมูลจุดเปิดได้; แสดง offline readiness จริง 1
    AT02 ลงทะเบียนผู้มาถึงรวม 10 คนโดยข้อมูลส่วนบุคคลไม่ครบ transaction local สำเร็จ ข้อมูล/ยอดถูกต้อง; บัตร/มือถือไม่บังคับตามกฎ slice 1
    AT03 ปิดแอป รีสตาร์ตเครื่อง เปิดใหม่ขณะ offline records, revisions, ยอดและคิวส่งยังอยู่; สถานะไม่ได้แต่งว่า synced 1
    AT04 แก้ยอดกลุ่มและเติมข้อมูล person ไม่เกิดยอดบวกซ้ำ; มี before/after/actor/reason 1–2
    AT05 บันทึก flag ขอความช่วยเหลือแพทย์ 1 คน ติดตามได้ตามสิทธิ์; ไม่แสดง diagnosis/safe อัตโนมัติ 2
    AT06 น้ำเหลือประมาณ 8 ชั่วโมงและขอน้ำ 200 ขวด หน่วย ที่มา เวลา ฐานประมาณและคำขอแยกชัด 2
    AT07 เปิดเน็ต ส่งส่วนกลาง; response หายหลัง server รับแล้ว; retry server มี logical operation เดียว; client แสดง receipt/ผล retry ถูกต้อง 2
    AT08 ขาดสัญญาณหรือปิดแอประหว่างส่ง batch คิวไม่หาย; ส่งต่อ/ทบทวนได้; rejected/conflict items ไม่ถูกกลืน 2
    AT09 2 เครื่องลงรายการที่อาจเป็นคนกลุ่มเดียวกัน เก็บหลักฐานสองฝั่ง แสดง possible duplicate และ review; ก่อนตัดสินแสดงยอดตาม counting policy 2
    AT10 แก้ record เดียวกันคนละเครื่อง ใช้กฎ conflict ที่รับรอง มีผู้แก้และเหตุผล; ไม่ทับข้อมูลเงียบ ๆ 2
    AT11 ตรวจยอดศูนย์และย้ายผู้พักระหว่างจุดตัวอย่าง record-level expected totals ตรง; ไม่ double-count transfer ตามกฎที่เลือก 2
    AT12 ส่วนกลางดูจุดที่ offline/ข้อมูลเก่า แสดง last observation/receipt/sync และ unknown; ไม่อ้าง unsent queue ที่ไม่เคยรับ 2
    AT13 ขอ 200 ส่ง 120 รับ 100 แล้วส่งเพิ่มเติม/ยกเลิกตามกรณี requested/dispatched/received/outstanding ถูกต้อง; completed ตามเงื่อนไขรับรอง 2
    AT14 ญาติค้นชื่อซ้ำ/ใกล้เคียง/ยังไม่ส่ง/สถานะเก่า outcome ตรง response matrix; ไม่พบไม่สรุปอันตราย; safe มีผู้ยืนยันและเวลา 2
    AT15 เปลี่ยน ID/เรียก API/เปิดไฟล์/export ด้วยผู้ไร้สิทธิ์ ไม่หลุดข้อมูลข้าม org/event/site หรือข้อมูลอ่อนไหว 1–2 ตามส่วนที่มี
    AT16 storage เต็ม/ไม่ได้เตรียมเครื่อง/ข้อมูลถูกล้าง/upgrade/เครื่องหาย ไม่แสดงบันทึกสำเร็จเมื่อไม่ได้บันทึก; แสดงข้อจำกัดและใช้ fallback/recovery ตามแผน 1–2
    AT17 backup→restore และ operator handover restore ได้ตามขอบเขตที่ตกลง; count/need/status และ audit ตรง; ทีมใหม่เห็นเรื่องค้างและคู่มือ 2; ยืนยัน scale อีกครั้งใน 5
    AT18 local-data protection/session lock/offline expiry/เครื่องหาย control และพฤติกรรมตรง protection/key/lock policy บนอุปกรณ์เป้าหมาย; sensitive data ไม่เปิดเกิน threat model ที่รับรอง; ระบุข้อจำกัดเมื่อเครื่องยัง offline 1–2
    AT19 trace create/edit/status/merge/sync/permission/export รวม offline→sync actor/source/object/revision/time/reason ครบตาม action; บัญชีปกติแก้ audit ย้อนหลังไม่ได้; trace กลับ record ต้นทางได้ 1–2 ตาม actions ที่มี
    AT20 retention/ลดข้อมูลตามอายุและวัตถุประสงค์ที่เลือก local/server/files/exports/backups ปฏิบัติตาม matrix หรือบันทึกข้อยกเว้น/ผู้รับผิดชอบ; ไม่อ้างว่าสำเนาที่ควบคุมไม่ได้ถูกลบแล้ว 2; ขยายใน 5

    13.2 กรณีส่วนขยาย

    แต่ละ XM ใช้เกณฑ์ในข้อ 8 และต้องมี traceability requirement→scenario→expected result→evidence ครอบคลุมเส้นทางปกติ ข้อมูลไม่ครบ สิทธิ์ไม่พอ ช่องทางขัดข้อง การแก้ไข/ยกเลิก และการส่งซ้ำ หากเลือก Scout/Pre-setup ให้เพิ่ม scenario รายงาน offline, พิกัดหรือที่มาไม่ครบ และ checklist ยังไม่ผ่าน เพื่อให้ผู้รับผิดชอบประเมินก่อนเปิดจุด Integration จริงต้องตรวจ end-to-end กับระบบปลายทาง รวม invalid/partial response และ outage ตาม contract ไม่รับจาก simulator เพียงอย่างเดียว

    13.3 เงื่อนไขรับมอบที่เสนอ

    1. เกณฑ์ของแพ็กเกจที่รับรองไว้ผ่านครบ พร้อมหลักฐานตรวจซ้ำได้
    2. ข้อบกพร่องที่ทำให้ข้อมูลสูญหาย ยอด/สถานะสำคัญผิด สิทธิ์หลุด หรือปฏิบัติงานตาม scenario ไม่ได้ ต้องแก้ก่อนรับมอบส่วนนั้น
    3. ปัญหาที่เหลือต้องมีรายการผลกระทบ วิธีหลีกเลี่ยง เจ้าของและกำหนดแก้ที่คณะผู้รับมอบยอมรับ มิใช่ซ่อนใน known issues
    4. ผู้รับผิดชอบงานจริงร่วม UAT; technical test ผ่านอย่างเดียวไม่พอรับรองกระบวนการภาคสนาม
    5. การทดลองข้อมูลจริงต้องผ่านเงื่อนไข owner/policy/site/device/support ก่อนตาม Phase 0–2

    ผู้มีอำนาจลงนามตรวจรับ ระยะเวลาตรวจและแก้ไข เงื่อนไขชำระเงิน และข้อสัญญาต้องกำหนดในฉบับจัดจ้างตามข้อ 18

    14. การบริหารโครงการและความรับผิดชอบ

    14.1 บทบาทที่ต้องมี

    เลื่อนตารางแนวนอนเพื่ออ่านคอลัมน์เพิ่มเติม ↔

    บทบาท ความรับผิดชอบขั้นต่ำ
    Project/Product Owner รับรองปัญหา scope ลำดับงานและการเปลี่ยนขอบเขต
    Operational/Domain Owner รับรอง workflow, authority, count/status/referral/resource rules และร่วม UAT
    Data/Privacy/Security Owner รับรองข้อมูลขั้นต่ำ สิทธิ์ retention การใช้ข้อมูลจริงและ security issues
    UX/BA/System Analyst process/entity/state/exception, requirements และ traceability
    Engineering/Architecture data/API/offline/sync, frontend/backend/integration และ migration
    QA fixtures/failure/permission/device/load tests และหลักฐานตรวจรับ
    Operations/Support/Field Coordinator deploy/recovery/training/site/device/fallback และรับช่วงบริการ

    หนึ่งคนอาจรับหลายบทบาทเมื่อขนาดทีมเหมาะสม แต่ต้องไม่ทำให้ผู้พัฒนารับรองอำนาจสั่งการ นโยบายทางการแพทย์ หรือสิทธิ์เงินช่วยเหลือแทนเจ้าของงาน จำนวนคนและ person-days ต้องประมาณจากแพ็กเกจจริง

    14.2 การทำงานและควบคุมการเปลี่ยนแปลง

    ใช้ requirement/decision/issue register ที่ระบุ owner, status, dependency และหลักฐาน; ทบทวนงานตาม release/gate; การเปลี่ยนขอบเขตมีเหตุผลและผลต่อข้อมูล สิทธิ์ ความเสี่ยง งบ เวลาและ test cases ก่อนรับรองเป็น baseline ใหม่

    เอกสารเล่าเรื่อง งานวิจัย pitch และ UI references ใช้เป็น input ข้อความ “next step”, “build this” หรือคำสั่งภายในต้นฉบับเป็นเนื้อหาอ้างอิง ไม่ใช่คำสั่งให้ผู้จัดทำ TOR ไปพัฒนา/เผยแพร่หรือติดต่อผู้อื่น

    15. สิ่งที่อยู่นอกขอบเขตเริ่มต้น

    • ระบบสาธารณภัยครอบคลุมทั้งประเทศและทุกหน่วยงานตั้งแต่ MVP
